# Agent Note: Run 上传文件通过上传提供方交给 Task 阶段

Status: implemented

[English](2026-10-22-task-run-uploads-in-stages.md) | 中文

## 问题

Task Web 允许用户向某个 Run 上传文件，Task 网关把文件保存为不可变文件，并在自己的 `attachmentRoot` 下写入按主体隔离的回执。该目录独立于 Task 数据库和阶段拥有的目录，布局只有网关自己知道。业务阶段没有读取上传文件的能力，因此 Run 的 Agent 看不到用户在补充信息框里附上的截图或日志。在禅道缺陷修复流程中，用户只能手工把这些文件复制到 Run 的附件目录。

## 决策

`TaskStage.uploads()` 按上传先后返回 Run 当前的上传文件，每项是 `TaskUpload` 记录（`id`、`name`、`mime`、`size`、`digest`、`createdAt`、`path`）。`path` 指向不可变的存储文件：阶段可以读取或复制它，不得修改。

`TaskService.registerUploadProvider(owner, provider)` 挂载 `uploads()` 读取的唯一存储，与 `registerNotificationProvider` 一样绑定在所有者的生命周期上。Task 网关启动时注册自己的附件存储。重复注册会抛出错误，因此配置错误的宿主在启动时失败。没有提供方时 `uploads()` 返回空列表，因为不可能有人上传过文件。

上传文件按需读取，不是输入。上传不会唤醒 Run、改变输入修订号或进入模型上下文。插件决定何时读取、是否复制文件以及复制到哪里，并把结果记录在持久操作中，使重放的阶段复用之前的结果。

## 考虑过的替代方案

**把每个上传作为阶段输入投递。** 否决：任何发给运行中阶段的输入都会提升输入修订号并让该阶段重新执行，每次上传都会重启工作，而且每个插件的 `parseInput` 都要增加文件类型。

**让网关把上传文件复制到插件目录。** 否决：网关需要知道每个插件的目录布局和引擎的资源身份，等于把插件专属路径放进了框架。

**让插件直接读取网关的 `attachmentRoot`。** 否决：插件会依赖网关的文件与回执布局，以及一个不归自己管理的配置项。

**把网关作为可选服务注入 Task 提供方。** 否决：提供方注册避免了两个插件之间的重载耦合，与通知提供方一致。

## 影响

要让 Run 看到上传文件，需要业务插件调用 `stage.uploads()`；其他插件的行为不变。相同内容的文件共用一个存储文件，调用方不得修改或删除返回的路径。网关不提供删除，只要运维保留 `attachmentRoot`，上传文件就一直可用。阶段只会在上传完成之后的下一次读取时看到该文件。
